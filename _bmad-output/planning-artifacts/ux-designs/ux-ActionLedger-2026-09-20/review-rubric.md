# Spine Pair Review — ActionLedger

Reviewed: `DESIGN.md`, `EXPERIENCE.md`, `mockups/review-screen.html`, `mockups/action-list.html`, `mockups/action-detail.html`. Sources read: `prd.md`, `addendum.md`, `docs/bmad-seed-prompt.md`. Calibration: internal, single-developer, three-day interview-demo build on Angular Material 3 with the prebuilt `azure-blue` theme; DESIGN.md is a semantic delta by design, so inherited Material base tokens are not flagged.

## Overall verdict

The pair is close to consumable. Every `{path.to.token}` reference in both files resolves to a frontmatter token, every color has a hex and a dark pair, all four PRD journeys are mirrored verbatim with protagonists, numbered steps, and climaxes, and the eight DESIGN sections and all required EXPERIENCE sections are present in canonical order. What blocks a clean source-extract is the component-name join between the two files: two DESIGN components are named differently in EXPERIENCE, five DESIGN brand components have no EXPERIENCE Component Patterns row, the Pending counter has a behavioral row but no visual spec, and EXPERIENCE uses an undefined name ("decision chip") for the human provenance chip. One seed-data dependency in UJ-2 is not surfaced. Fixing the naming joins and adding six short rows makes this pair strong; nothing needs redesign.

## 1. Flow coverage — adequate

Extracted UJ-1 through UJ-4 from `prd.md` §2.4 and checked each against Key Flows for verbatim name, named protagonist, numbered steps, a climax beat, and a failure path. All four names match the PRD character for character. UJ-1, UJ-2, and UJ-4 have protagonist, steps, climax, and failure. UJ-1 covers the PRD edge case (malformed output twice) and the addendum's unmatched-owner storyline. UJ-4 documents why it opens seeded Meeting 3 instead of the UJ-1 live run. Also checked that every IA surface is reached by at least one flow: Login (UJ-2), Meeting List and Meeting Detail (UJ-1), Review Screen (UJ-1, UJ-3), Action List and Action Detail (UJ-2, UJ-4). Run Detail is reached only by a failure branch (UJ-1 failure) and is never opened as a success surface; acceptable since no PRD journey visits it.

### Findings
- **medium** UJ-2's climax needs seed data that the addendum does not describe. The climax shows an Audit Trail in the office move Meeting with an AI-proposed due date of 2026-09-26 edited by Dana to 2026-09-12. The addendum seed storyline defines Meeting 1 as "five approved, one rejected" with no Edited action; only Meeting 3 has an edit, and that edit is owner and due date on the P. Ram action. PRD UJ-2 itself says "the due date was set by Dana on approval," which implies an edit, so the source is internally loose, but the spine silently resolves it by inventing an Edited action and two dates (EXPERIENCE.md, Key Flows, UJ-2 steps 4 and 5). *Fix:* either point UJ-2 at the Meeting 3 action, or add "Meeting 1 needs one Edited action whose due date Dana moved earlier, so the Overdue row Marcus opens has a Was/Now due-date entry" to the Open Questions "Needs from" paragraph so the FR-35 seed story carries it.
- **low** UJ-3 has no climax beat and no failure path, although the PRD defines an edge case for it (receiver down, retries visible in the API). The spine correctly scopes UJ-3 out of the Angular surface (EXPERIENCE.md, Key Flows, UJ-3). *Fix:* one line: "Failure: receiver down. Retries and the Dead state are visible only through the API and the receiver page; nothing changes in the Angular app."
- **low** No flow exercises FR-17 (status change) or the Lead-only Cancelled boundary that the PRD calls "the one write that distinguishes the two Roles in v1, so the demo can show authorization working." The behavior is fully specified in the Status control row, so this is a demo-script gap, not a spec gap. *Fix:* optional two-step addendum to UJ-2 ("Marcus sets the action to In Progress; the Undo snackbar appears") or leave for DEMO.md.

## 2. Token completeness — adequate

Extracted all 28 color tokens, 2 typography roles, 4 rounded tokens, 8 spacing tokens, and 17 component token objects from the DESIGN.md frontmatter, then every `{path.to.token}` reference in DESIGN.md prose (33 distinct references) and EXPERIENCE.md prose (3 distinct references). Every reference resolves by name to a frontmatter token. Every color has a hex; every semantic family has light and dark triples (base, container, on-container) or pairs (neutral). Recomputed every stated contrast pair: all claims hold and the stated numbers are conservative (light on-container pairs measure 8.7:1 to 12.4:1, dark pairs 8.2:1 to 10.1:1, the unstated Material `on-surface` on `ai-provenance-container` pair measures 13.3:1 light and about 8.2:1 dark, and the amber left border measures 5.9:1 on `surface-container-low`, above the 3:1 non-text floor). Typography roles define family, size, weight, and line height. Material-inherited roles are named semantically (`headline-small`, `title-medium`, `body-medium`, `body-small`, `label-large`), which the calibration permits.

### Findings
- **medium** `components.audit-entry-ai` defines `marker` and `background` but no `foreground`, and its background is the purple container (DESIGN.md frontmatter lines 124 to 126, Components "Audit entry"). The AI Proposal entry carries the most text of any entry (all five proposed fields plus Source Excerpt), so a story developer must guess between `on-ai-provenance-container` and Material `on-surface`. `proposal-card` also omits `foreground` but sits on a Material surface, so inheritance is unambiguous there. *Fix:* add `foreground: '{colors.on-ai-provenance-container}'` (or `'material.on-surface'`, as `source-excerpt-highlight` does) to `audit-entry-ai`.
- **low** The `material.<token>` string convention used in seven component values (`material.error-container`, `material.primary-container`, `material.on-surface`, `material.surface-container-low`, and their on-pairs) is never declared. It is the right pattern for UI-system inheritance, but the frontmatter comment on line 8 only says unlisted tokens inherit; it does not say that a bare `material.x` string means the Angular Material system token `--mat-sys-x`. *Fix:* one comment line in the `components` block: "`material.<name>` strings are Angular Material 3 system tokens (`--mat-sys-<name>`), not frontmatter tokens."
- **low** `typography.confidence-score` uses Roboto Mono, which Angular Material does not ship; the default `index.html` loads only Roboto and Material Symbols. Not a token defect, but the only external asset the delta introduces. *Fix:* note in Typography that Roboto Mono must be added to the font link, or fall back to `ui-monospace`.
- **low** Unreferenced tokens: `rounded.md` and the `spacing` scale `'1'` through `'6'` (with `'5'` absent) are defined but never referenced in either spine; only the three named spacing tokens are used. Harmless, but a consumer mirroring the frontmatter will emit dead tokens. *Fix:* drop the numeric scale and `rounded.md`, or keep them and say "scale listed for completeness" in the comment.

## 3. Component coverage — thin

Extracted every component name from DESIGN.md Components (8 brand components: Provenance chip, Low Confidence badge, Overdue indicator, Status chip, Review State chip, Proposal card, Source Excerpt highlight, Audit entry; plus 13 Material components listed as unchanged), from DESIGN.md frontmatter (17 component token objects), from EXPERIENCE.md Component Patterns (17 rows), and from every other EXPERIENCE section and the mockups. Checked each for an entry in both DESIGN.md.Components and EXPERIENCE.md Component Patterns under the same name. Proposal card is the only brand component that joins cleanly in both directions, and its two entries are genuinely complementary (anatomy in DESIGN, edit-mode and decision behavior in EXPERIENCE).

### Findings
- **high** Two brand components are named differently across the spines, so a name-keyed join fails. DESIGN "Source Excerpt highlight" (Components, and token `source-excerpt-highlight`) is specified behaviorally in EXPERIENCE as "Source Excerpt link" (Component Patterns row 10). DESIGN "Audit entry" (tokens `audit-entry-ai`, `audit-entry-human`) is specified behaviorally as "Audit Trail timeline" (Component Patterns row 16). The content is compatible; the names are not. *Fix:* rename the EXPERIENCE rows to "Source Excerpt highlight" and "Audit entry" (keep "Audit Trail timeline" as the container if wanted, but then give DESIGN a matching "Audit Trail timeline" entry for the line and marker geometry).
- **high** EXPERIENCE uses the undefined name "decision chip" for what DESIGN calls the human provenance chip: Proposal card row ("replaces the controls with the decision chip, timestamp, and Review State chip") and Accessibility Floor ("the Pending counter and the decision chips are in an `aria-live` region"). A reader cannot tell whether "decision chip" is the provenance chip, the Review State chip, or both. *Fix:* replace with "human provenance chip" in both places, and state in Accessibility Floor which chips are live-announced.
- **medium** Five DESIGN brand components have no EXPERIENCE Component Patterns row: Provenance chip, Low Confidence badge, Overdue indicator, Status chip, Review State chip. Their behavior is scattered across Provenance Language, State Patterns ("Overdue", "Low confidence proposal"), and the Proposal card row, so nothing is unspecified, but the rubric contract is one row per component and a story author looking up "Status chip" in Component Patterns finds nothing. *Fix:* one compact row "Indicator chips (Provenance, Low Confidence, Overdue, Status, Review State)" stating: non-interactive, icon plus text always, text is the PRD state name, driven by API fields (`isLowConfidence`, `isOverdue`, Review State, Action Status), never color alone.
- **medium** The Pending counter has a behavioral row (Component Patterns row 11) and the DESIGN Colors prose says "Pending-count chips" sit on the neutral container, but there is no `components.pending-counter` token and no Components entry, and the two spines use different names for it. The review-screen mockup renders it as a chip. *Fix:* add `pending-counter` to the DESIGN frontmatter and Components ("`mat-chip` on `{colors.neutral-container}`, text from EXPERIENCE Pending counter, becomes the success container when it reads 'All proposals decided'" or stays neutral, decide once), and use "Pending counter" in DESIGN Colors.
- **medium** The human provenance chip's content is stated two ways inside EXPERIENCE. Provenance Language says the chip reads "Decided by {name} · {timestamp}" (timestamp inside the chip). The Proposal card row and the review-screen mockup put the timestamp beside the chip, and DESIGN says the chip text is "Decided by {display name}" only. *Fix:* pick DESIGN's version and fix the Provenance Language cell to "'Decided by {name}' chip with the timestamp beside it."
- **low** The Material inherited list (DESIGN Components, first paragraph) omits three components EXPERIENCE relies on: `mat-slide-toggle` (Filter bar "Overdue only" toggle), `mat-menu` (Toolbar user menu; DESIGN Elevation already mentions "the user menu elevate"), and `mat-chip-grid` with `mat-chip-row` (New meeting dialog attendee chip input). `mat-date-range-picker` is implied by `mat-datepicker`. *Fix:* add the three names to the inherited list.
- **low** Two EXPERIENCE rows have no Material or DESIGN counterpart at all: "Run metadata block" (a two-column definition list) and "Run list" (unstated whether table or list). Both are on Run Detail, a non-hero surface, so a default is acceptable. *Fix:* say `mat-table` for Run list and "definition list, `body-small` labels, `body-medium` values" for the metadata block, or declare both as plain HTML.

## 4. State coverage — adequate

Walked all seven IA surfaces plus global against the applicable state set (cold load, empty, in-progress, error, permission-denied, conflict, terminal, focus). Covered well: cold load for every table and detail; empty Meeting List; Meeting without notes; extraction in progress and Failed; run warnings; zero proposals; all decided; low confidence; unmatched owner; no filter matches; Overdue; terminal status; 401 with route restore; 403 with the Lead-only control disabled; 409 with reload and no retry; write failure with retry; offline explicitly declined with a reason. Focus states are delegated to Material defaults in the Accessibility Floor, which the calibration permits.

### Findings
- **medium** No read-failure state. State Patterns covers "Save failure or network error" for "Any write" only. A failed GET (API down, 500, or a network error on cold load) has no treatment on any surface, and the demo's step 1 is a cold load. *Fix:* one row: "Load failure | Any table or detail | Progress bar stops; body shows 'Couldn't load. {problem detail title}' with a Retry button. Filters and the toolbar stay usable."
- **medium** Two Pending-card input states from FR-5 and FR-15 are not covered: a null suggested due date and an empty suggested owner. The review-screen mockup invents "No due date proposed" for the first and shows an empty owner with "AI suggested: Facilities" for the second, but the spine's Proposal card row and State Patterns say nothing about either, so the mockup, not the spine, is currently the source. *Fix:* add a State Patterns row "No suggested due date or owner | Review Screen | Due date reads 'No due date proposed'; owner reads 'Unassigned' and the hint reads 'AI suggested: none' when the suggested text is empty."
- **low** No in-flight state for the three card actions. Approve, Reject confirm, and Approve with edits have no disabled-while-pending rule, so a double click produces a 409 and the "Already changed. Reloading." snackbar on the user's own action. *Fix:* add to Interaction Primitives: "Buttons that start a write disable until the response returns."
- **low** No not-found state for `/meetings/:id`, `/meetings/:id/runs/:runId`, or `/actions/:id`. Low for a seeded demo. *Fix:* one row: "404 | Any detail route | 'Not found.' with a link to the parent list."
- **low** Cold load specifies "5 skeleton rows," but Angular Material has no skeleton component, so the developer builds one. DESIGN does not mention it. *Fix:* either drop skeleton rows and rely on the progress bar, or add a one-line `skeleton-row` spec in DESIGN Components (`surface-container-highest`, `{rounded.sm}`, row height matching density -1).

Decided cards in the mockup drop the Source Excerpt and the read-only field labels; UJ-1 step 5 says a card "collapses," but the Proposal card row says only that the controls are replaced. *Fix:* state in the Proposal card row whether a decided card keeps its Source Excerpt (recommended: keep it, since Provenance Language says the excerpt is how AI provenance is shown).
